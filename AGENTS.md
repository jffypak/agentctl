# Tinkerbell

You are working inside a project that uses **Tinkerbell** — a portable, local-first, agent-native personal operating system. This file is assembled from numbered fragments under `.tinkerbell/prompts/protocol-fragments/` and regenerated by `.tinkerbell/scripts/assemble_md.py`. Content outside the sentinels is preserved.

Tinkerbell has four user-facing layers — **curated memory** (stable doctrine in `.tinkerbell/memory/curated/`), **episodic memory** (raw history in `.tinkerbell/state/episodic/tinkerbell.db`), **graph memory** (deferred to Phase 3), and **hooks + router** (load context on demand under a token budget). The next section is the **map**: it tells you *where* each rule lives. After the map, this file contains only the must-follow rules; deeper docs — architecture (`docs/ARCHITECTURE.md`), phase state (`docs/kanban.md`), agents, skills, extensions, profiles — are linked from the map and live in their canonical homes.

# Memory model (critical)

**Never confuse these three layers:**

| Layer | Answers | Storage | When to write |
|---|---|---|---|
| Curated | "what matters repeatedly?" | `.tinkerbell/memory/curated/*.md` | Only when the 4-condition capture gate passes |
| Episodic | "what happened?" | SQLite (`.tinkerbell/state/episodic/tinkerbell.db`) | Append-only; ingest via `.tinkerbell/scripts/episodic_ingest.py` or the API |
| Graph | "how is this connected?" | (Phase 3, not built yet) | N/A in Phase 1 |

## Capture gate for curated memory

Before writing to `.tinkerbell/memory/curated/`:

1. **Reusable** across multiple sessions
2. **Non-obvious** — not recoverable from reading the code
3. **Stable** — unlikely to change in weeks
4. **High-confidence**

Why > what. Code already documents the "what"; memory carries rationale.

## What does NOT belong in curated memory

- Raw transcripts or session details → episodic
- Single-file facts recoverable by `grep` → just read the file
- Ephemeral TODOs → `.tinkerbell/memory/curated/work/<slug>/`
- Active debugging narratives → `.tinkerbell/memory/curated/threads/<topic>.md`

# Retrieval protocol

When you need background, context, or prior knowledge:

1. **Search memory before grepping the codebase.** Curated memory often has the *why* that grep can't surface.
2. Use the context router: `python -c "from tinkerbell.context import load_context, render_blocks; print(render_blocks(load_context('<your question>')))"`.
3. The router decides which layer(s) to load under a hard token budget. It logs every decision to `.tinkerbell/state/provenance/YYYY-MM-DD.jsonl`.
4. If the router returns no blocks, that's the right answer — do the simple implementation directly without invented context.

## Routing hints (not exhaustive)

- Architecture / convention / pattern / "why do we" → curated (keyword fast path)
- Any other phrasing → the router asks the curated store directly and loads
  its best entry if that entry clears the relevance floor. You do **not** have
  to phrase a question in doctrine vocabulary to reach memory.
- "last time", "what happened", "before", "previously" → episodic
- "connected", "depends on", "impact of" → graph (Phase 3, currently deferred → falls back to curated + episodic)
- Simple implementation ("write a function…", "fix this bug") → no retrieval,
  unless the store holds doctrine plainly about the thing you are editing

## Provenance requirement

Every retrieved context block has provenance. If you are about to act on a piece of retrieved content and are uncertain where it came from, check the most recent line in `.tinkerbell/state/provenance/YYYY-MM-DD.jsonl`.

# Capture protocol

During a session, if you notice a durable lesson worth preserving:

- Brief (<1 paragraph): write to `.tinkerbell/state/pending-captures/<slug>.md`. The next session's SessionStart hook will surface it for review.
- Fully formed curated entry: write directly under `.tinkerbell/memory/curated/<category>/<slug>.md` with the frontmatter:

```yaml
---
title: <short, declarative>
category: <one of: principles|architecture|conventions|workflows|gotchas|abstractions>
created: <YYYY-MM-DD>
confidence: <high|medium>
tags: [tag, tag]
why: "<one-sentence rationale>"
---
```

Body: explain the decision, its context, and the key tradeoffs. Keep it inspectable.

Target cadence: 2–5 captures per substantial session. Fewer is fine. Zero is fine.

# Work items

Multi-step, multi-file, or cross-session tasks belong in `.tinkerbell/memory/curated/work/<slug>/`:

```
memory/curated/work/<slug>/
├── _meta.json     # slug, created, branch, links
├── plan.md        # spec + plan
├── tasks.json     # checklist (optional until Phase 2)
└── notes.md       # running log
```

Do **not** rely on Claude Code's built-in plan mode for anything that should outlive the session — plans there disappear.

Check `.tinkerbell/memory/curated/work/` before exploring `git log` or branches for the history of active tasks.

# Hooks

Tinkerbell wires four Claude Code hooks (see `.tinkerbell/hooks/hooks.json`):

| Hook | Behavior |
|---|---|
| `SessionStart` | Surfaces pending captures from the previous session, if any. Does **not** preload memory. |
| `Stop` | **Budgeted** reflection prompt — usually silent. See below. |
| `PreCompact` | Block-with-reason before context compaction, skipped if the session edited nothing. |
| `PreToolUse` | Logs every tool call to `.tinkerbell/state/hooks/YYYY-MM-DD.jsonl` AND consults `tinkerbell.guardrails` — block-with-reason on a rule match. See "Guardrails" below. |

All hooks fail open — a hook error never breaks the session. Each is timeout-bounded (5–10 seconds).

If you want to disable a hook temporarily, set `tinkerbell.hooks.enabled.<name>: false` in `.tinkerbell/config/local/machine.yaml`.

## The reflection budget

**`Stop` fires after every assistant turn, not once per session.** Every block
costs a full extra inference pass over the whole context window, and the
reason text stays in context for the rest of the session. So reflection is
rationed by `tinkerbell.reflection`, which gates on three questions in order:

1. **Substance** — did the session edit anything? (`min_edits`, default 3.)
   Read-only and Q&A sessions never trigger reflection.
2. **Backoff** — the bar multiplies after each fire (`growth`, default 4.0),
   so prompts land at 3, 12, then 48 edits — not every turn.
3. **Cap** — `max_fires` (default 3) per session, regardless of volume.

Counters live in `.tinkerbell/state/hooks/reflection.json`, keyed by session id, pruned
after `retention_days`. Tune any of it under `hooks.reflection` in
`.tinkerbell/config/defaults.yaml`.

Every decision — fired or suppressed — logs with `level: budget`, so the rate
is auditable:

```sh
jq -r 'select(.level=="budget") | .code' state/hooks/*.jsonl | sort | uniq -c
```

When it does fire, the prompt is deliberately terse: it names the variable
facts (edit count, queued capture slugs, handoff state) and points at
`/tb:remember` and `/tb:handoff`. It does **not** restate the capture gate —
that doctrine already lives in this file, and re-teaching it every turn was
the original bug.

# Guardrails

The PreToolUse hook consults `tinkerbell.guardrails` before every tool call.
If a rule matches, the hook returns a Claude Code block-with-reason — the
call never executes, the agent sees the reason, and chooses whether to
reformulate or escalate.

## What is blocked (Phase 2.0)

| Rule id | Blocks |
|---|---|
| `fs_destruction` | `rm -rf /`, `rm -rf $HOME`, `rm -rf .`, `rm -rf ..`, `rm -rf .git` |
| `git_force_protected` | `git push --force` / `git reset --hard <branch>` / `git branch -D <branch>` / `git push origin :<branch>` against `main`, `master`, `prod`, `production`, or `release` |
| `prod_db` | `DROP DATABASE` / `DROP TABLE` / `TRUNCATE` / unscoped `DELETE FROM` on a command containing a prod indicator (`prod`, `production`, `_prod`, `-prod`) |
| `tinkerbell_integrity` | `rm` of `.tinkerbell/state/episodic/tinkerbell.db` or `.tinkerbell/state/graph/tinkerbell-graph.db`, and direct `Write`/`Edit` to those SQLite files |
| `secrets_in_command` | AWS access keys (`AKIA…`), GitHub tokens (`ghp_…`), Slack tokens (`xox[abprs]-…`), OpenAI / Anthropic keys, `--password=…` on argv |
| `pipe_to_shell` | `curl … \| sh`, `wget … \| bash`, including `sudo` variants |

The full predicate set, with rationale, lives in
`.tinkerbell/src/tinkerbell/guardrails.py`. Tests in `.tinkerbell/tests/test_guardrails.py` are the
canonical "this is what gets blocked" reference.

## How a block looks

When a rule matches, the agent receives a tool-result like:

```
[tinkerbell guardrail: fs_destruction] Refusing recursive force-delete of a
critical path (`/`, `$HOME`, `.`, `..`, `.git`). If this is intentional,
delete the specific subdirectory by name.
```

Default response: **reformulate** to the narrower, safer command. Escalate
to the user only if the original command really was the right one.

## Configuring guardrails

All knobs live under `guardrails:` in `.tinkerbell/config/defaults.yaml`. Per-machine
overrides go in `.tinkerbell/config/local/machine.yaml` (gitignored). You can:

- Disable a single rule: `guardrails.rules.<rule-id>.enabled: false`
- Disable everything: `guardrails.enabled: false`
- Add to `protected_branches` or `prod_indicators`
- Rename `override_env`

## One-shot override

Sometimes a destructive op really is the right call. Set the env var named
in `guardrails.override_env` (default `TINKERBELL_OVERRIDE_GUARDRAIL`) to a
rule id, or `*` to disable all rules:

```sh
TINKERBELL_OVERRIDE_GUARDRAIL=git_force_protected git push --force origin release-test
```

Overrides are logged to `.tinkerbell/state/hooks/<date>.jsonl` so you can audit who
bypassed which rule and when.

## Adding a new rule

1. Add a predicate + `Rule(...)` entry to `_default_rules()` in
   `.tinkerbell/src/tinkerbell/guardrails.py`.
2. Add a row to the table above.
3. Add positive + near-miss test cases to `.tinkerbell/tests/test_guardrails.py`.
4. Add a toggle to `.tinkerbell/config/defaults.yaml` under `guardrails.rules`.

A new rule earns its place if it (a) catches an *unambiguously* destructive
shape, (b) has near-zero false-positive risk, and (c) describes a class of
mistake real users could plausibly make. When in doubt, leave it off —
false positives erode trust faster than missed blocks.
